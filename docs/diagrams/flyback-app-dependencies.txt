# Flyback.App dependency graph — construction-time only (ADR-0150)
# One container per editor window (EditorServices.cs, CanvasServices.cs, WindowServices.cs).
# Everything not flagged [ext] lives in Flyback.App; [ext] = Flyback.Ui/Engine/Plugins.
#
# This is the plain-text edge list (diffable, grep-able). The same data renders as two
# pictures: flyback-app-dependencies.svg (everything except the canvas subsystem, which
# is collapsed to one NodeEditor node) and flyback-app-canvas-internals.svg (just the 17
# classes CanvasServices.cs registers, which nothing outside it depends on but NodeEditor
# itself). Split in two because the canvas subsystem is a near-clique on its own scale;
# drawn in the same picture as the composition root it turned into an unreadable tangle.
#
# Usage (a telemetry sink most classes hold, like a logger) is left out of this list
# entirely: nearly every class takes it, and it is a hub with no structural meaning to
# trace, not a real collaborator.
#
# Legend
#   [R]      registered in the editor's DI container
#   A -> B   A takes B (or an interface B implements) as a constructor parameter (DI)
#   A ~> B   A takes Lazy<B> — deferred DI, breaks a cycle (ADR-0150)
#   A => B   A does `new B(...)` in its own constructor or a field initializer — NOT DI
#
# Interface -> implementation registrations (container never sees the interface name below the dash)
IAssistantEditor => AssistantEditor
IDialogs => WindowDialogs
IFilePickers => WindowFilePickers
IMonitors => WindowMonitors
IWindowFocus => WindowFocus
IWindowClose => WindowClose
IPointerAnchors => PlatformAnchors        [ext, pre-built instance, not container-constructed]
