# ADR-0016: Build the UI in C#, without XAML

**Status:** Accepted · 2026-08-11

## Context

Avalonia's documented path is XAML plus code-behind, with `AvaloniaBuildTasks`
compiling `.axaml` files and generating partial classes. It also fully supports
constructing the visual tree in C#.

This shell has an unusual shape for a XAML app. Two of its four regions — the
node editor and the preview — are single custom-drawn controls with no internal
markup ([0017](0017-draw-the-node-editor-in-one-control.md)). A third, the
palette, is generated by looping over `NodeCatalog`. The fourth, the inspector,
is rebuilt from scratch whenever selection changes, because its contents depend
entirely on the selected module's port list.

So three of four regions are constructed programmatically regardless of whether
XAML is in the project.

## Decision

No XAML. `SynthApp` adds `FluentTheme` to `Styles` in code, `MainWindow` builds
its layout in `BuildLayout()`, and there are no `.axaml` files.

## Consequences

The inspector — the most dynamic part of the UI — is a plain method that returns
controls. Under XAML it would need an `ItemsControl`, a `DataTemplate` per port
kind, a template selector, and a view model per row, to produce the same three
widgets. `BuildInputRow` is 86 lines and does the whole job, including the
two-way slider/numeric sync and the patched-input case.

The palette is a `foreach` over `NodeCatalog.Categories`. New modules
([0008](0008-modules-as-data-in-one-catalogue.md)) appear with no markup change,
because there is no markup.

No binding layer means no view models, no `INotifyPropertyChanged`, and no
question about where state lives — it lives in the `Patch`. Wiring is direct
event handlers, and the compile trigger is one line: `_editor.PatchChanged += (_, _) => Recompile();`

It also removed a whole class of build risk. The XAML compiler is version-
sensitive, and this was Avalonia 12 rather than the 11.x the ecosystem's
documentation mostly describes. Pure C# meant the only thing that could fail was
the C# compiler, which was worth something when validating an unfamiliar major
version.

The costs are real. There is no designer preview and no hot reload, so layout
changes require a rebuild. Layout is more verbose than markup — `BuildLayout`
plus `BuildToolbar` and friends run to about 200 lines that XAML would express
more compactly. And it is not what an Avalonia developer expects to find, which
is why the structure is kept to one `Build*` method per region.

For a larger app with genuinely declarative screens this would be the wrong call.
For a four-region tool where the interesting surfaces are custom-drawn, the
markup would mostly have been scaffolding around controls built in code anyway.
