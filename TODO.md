# To do

Work the user has asked for and nobody has started. Take an item off when it lands on `main`.

- **Replace the presets' repeated formulas with modules.** A Window (on between two points, soft or hard edged) and a Dice (a stable random for a whole number), then port the presets onto them. Which formulas, how many, where, and what was ruled out are in [docs/handoff/formulas-into-modules.md](docs/handoff/formulas-into-modules.md).

- **Finish the web editor (ADR-0162).** The processor's preview, which draws a patch that plays a sample at 3 frames a second on the page's one thread.
- **`--trace <file>` on the editor and the viewer.** Writes every stall over 100 ms on the UI thread, in the picture's drawing and in the sound callback, with the step it was in (`SetPatch`, a GL call, `Recompile`, `Transport.Load`), so a freeze report is one command rather than a hand-built probe.
- **Loop any stretch of the seek bar.** Two handles on the bar set where a loop starts and ends, so a passage in the middle of a piece repeats rather than always the start.
- **Step a paused patch a frame at a time.** Left and right arrows over a paused full-screen picture, in the editor and the viewer, move the clock one frame back or on, for looking at what a picture does at one instant.
- **Count which features and modules are used.** The usage events (`src/Flyback.Editor/Statistics/Usage.cs`) say how many modules a played patch has, not which ones, and nothing about which editor features are reached for. Add both to what is sent to Aptabase, inside what ADR-0094 allows: shipped modules and features by name, a plugin's own under one name, nothing that could tie a report to a person or a patch.
- **`flyback-viewer --report`.** At the end of a run, print the frames a second it held, the slowest frame, what the sound cost, and which backend drew the picture (GPU or processor, with the GPU's refusal where it fell back), so a script or an agent can measure a patch and know what drew it without watching it.
- **Find why the web viewer's sound renders slower than the web editor's.** Acid at 2× ran at 1.1× real time under the viewer and 4× under the editor, on one worker, so the viewer steps down to 1× where the editor holds. The measurement and the leads are in [docs/handoff/viewer-sound-slower-than-editor.md](docs/handoff/viewer-sound-slower-than-editor.md).
- **The web viewer reports its sound's speed live.** `speaker.js` measures nothing for the JavaScript sound, so the status line shows only dropouts, and a phone slowing as it heats up is invisible until the sound stutters. Report the seconds rendered per second spent every couple of seconds, show it in the status line, and warn when it falls towards 1× rather than only once its chunks keep coming late.
- **`flyback-cli info --by-group`.** List each group's picture and sound ops, and `--json` them, so finding what makes a patch heavy is one command rather than a scratch test that deletes a group at a time and recompiles. A group the Output depends on (a desk, a master) is counted by what it adds, not by everything upstream of it.

The contract, the plugins and the file-level sequence are in [docs/handoff/decision-model.md](docs/handoff/decision-model.md).
- **Fix what a finger still cannot do.** Thirteen touch bugs left, on a touch screen on the desktop and in the page: the sound held back on an iPhone, keys with no button, the on-screen keyboard over the code view and the field being typed in, wires lost to the socket snap, a two-finger pan that edits, holes in the finger state machine, sliders that change on a scroll. Each with its cause, a repro to check on a phone first, and a fix hint, in [docs/handoff/touch-bugs.md](docs/handoff/touch-bugs.md).
- **Take the long synchronous work off the UI thread.** Cache the assistant's key lookups, load a patch's samples before compiling it, and move plugin install, bundle save and the Linux file-type refresh off the UI thread. The audit, with each site, its fix and what was ruled out, is in [docs/handoff/sync-to-async.md](docs/handoff/sync-to-async.md).
- **A spending limit the host keeps.** Count each assistant session's requests in the transport and stop past a bound, and add up the token use `ModelReply` reports against a daily budget the user sets in Settings → Assistant, so a runaway or buggy plugin cannot spend without end. A hostile allowed plugin reads the stored key instead, so this caps accidents, not theft.
- **`flyback-cli render --mute <group>` and `--solo <group>`.** Mute switches a group's modules off for the run (ADR-0117); solo switches off every module that is neither upstream of the group nor on its way to the Output, so a part is heard alone with its own echo and room. Balancing Flyback Theme took eight rebuilds to learn that the lead, not the pad or the arp, was the chorus's 800–2,500 Hz bulge; one solo would have said so.
- **A Release `flyback-cli` built on its own loads the shipped plugins, and says when it did not.** Only `Flyback.App` and the test projects lay out `plugins/` with the `plugins.sha256` that trust needs (ADR-0158), because the CLI publishes into the App's folder, so `dotnet build src/Flyback.Cli -c Release` loads none. Its build, not its publish, should lay them out as the App's does. The refusal report goes to stderr only when stderr is a terminal, so behind a pipe `info --preset Outrun` says only that no preset has that name; a missing preset, module or assistant should name the refused folders, and a global `--verbose` prints the plugin report whatever stderr is. `ask` behind a pipe said only that no assistant was installed when every plugin had been refused as built against another contract.
- **A live-patching mode.** A desktop-only editor mode where the picture fills the screen and the patch is edited over it, as either the canvas or the text view, for playing a patch live in front of people.
